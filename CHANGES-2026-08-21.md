## 1. The phone was not being discovered

Starting symptom: the PC was joined to the phone's hotspot, but the detector
never found the phone and alerts silently went nowhere.

Measured state of the link:

| | |
|---|---|
| Phone (hotspot AP) | `10.106.225.122` |
| PC | `10.106.225.177/24`, adapter `Wi-Fi 2`, profile Public |
| PC adapters total | 10 IPv4, incl. Tailscale, VirtualBox, OpenVPN, 2 link-local |

Windows Firewall was ruled out — enabled inbound Allow rules already exist for
`python.exe` (3.11 and 3.14) covering the Public profile, with no blocking
rules.

### Correction to the first diagnosis

The initial conclusion was that the phone's broadcast never reached the PC,
because `DiscoveryBroadcaster` created its socket unbound and Android would
bind it to the default network (mobile data while tethering).

**That turned out to be wrong on this setup.** A passive 15-second listen on
UDP 9876, sending nothing, captured **7 announcements from `10.106.225.122`**
at the expected 2-second interval — from the *old* app. The broadcast does
arrive.

The operative fault was on the PC side: last-packet-wins (section 4). The
broadcaster rewrite (section 2) is still a real robustness improvement and
carried two genuine bug fixes, but it was not the blocker. Commit `5832ee4`'s
message reflects the original, incorrect reading; `1c5e586` is the accurate
record.

## 2. Broadcaster announces per interface — `5832ee4`

`DiscoveryBroadcaster.java` sent a single packet to `255.255.255.255` from an
unbound `DatagramSocket`. Android binds an unbound socket to the *default*
network, which is mobile data while the phone serves a hotspot.

Now it enumerates live non-loopback interfaces and sends to each one's own
subnet-directed broadcast address, so the kernel routes each packet out that
interface with a matching source IP for the PC to reply to. Point-to-point
links such as cellular report no broadcast address and drop out on their own.

This also handles a **randomized tether subnet** — this phone hands out
`10.106.225.x`, not the classic `192.168.43.x`, so a hardcoded fallback would
have missed it.

Global broadcast is kept only as a last resort, when enumeration returns
nothing. Sent alongside the per-interface addresses it is actively harmful: in
testing it left via the VirtualBox adapter and overwrote a correctly
discovered peer with `192.168.56.1`.

Two further bugs fixed here:

- **Truncated replies.** The receive `DatagramPacket` was reused across calls.
  `receive()` shrinks a packet's length to the bytes read, so every reply
  after the first was silently truncated. A fresh packet is now allocated each
  time.
- **`stop()` did not stop.** It called `interrupt()`, which does not interrupt
  `DatagramSocket` I/O. It now closes the socket, which does.

The loop also stays in `receive()` for the whole cycle instead of sleeping
blind, so a reply is picked up as soon as it lands.

## 3. Discovery validated and locked — `1c5e586`

`discovery.py` accepted any packet whose `service` field matched and
overwrote whatever it had found before. On a machine with ten adapters, a
stray announcement retargets every alert at an address the phone cannot
receive on, and nothing in the output says so.

It now accepts the **first** peer that passes validation and locks to it:

- ignores our own broadcasts echoed back — otherwise the detector "discovers"
  itself and alerts its own address, which was reproduced in testing
- ignores loopback and link-local sources; a phone on the hotspot never has one
- ignores a peer with no usable route back, rather than replying with an
  unreachable `pc_ip`
- keeps answering re-broadcasts from the locked peer, so a phone that missed
  the first reply still learns the PC address, but never re-fires the callback

Rejections are logged once per source, since announcements repeat every 2s.

**Silent-failure fix.** `PHONE_IP` is `None`, and the watchdog used to call
back with `None` after its 10-second timeout, leaving the HTTP client aimed at
nothing. That failure mode looks exactly like a working system that never
alerts. It now warns that phone alerts are disabled and says what to check.

Verified against the live phone:

```
[DISCOVERY] Phone detected at 10.106.225.122:5000, PC IP is 10.106.225.177
[DISCOVERY] Ignoring announcement from 192.168.56.1 — already locked to 10.106.225.122
```

## 4. The repo could not be built from a clean clone — `aa81a44`

`gradle/wrapper/gradle-wrapper.properties` was committed, but `gradlew`,
`gradlew.bat`, and `gradle-wrapper.jar` were not. Without them there is no
`./gradlew`, so building required a matching Gradle already installed and
located by hand.

The wrapper is now committed, pinned to Gradle 8.14 — the version this project
is verified against. `gradlew` has its exec bit set.

The README gained an **Android Alert App** section covering what is not
discoverable from the source:

| Requirement | Why it bites |
|---|---|
| JDK 17 | AGP 8.2.0 cannot parse Java 21+ version strings. On JDK 25 the entire error message is the literal text `25.0.2`. |
| SDK platform 34 + build-tools 34.0.0 | `compileSdk = 34`; the machine had 28/31/33/36 and build-tools 35/36 only. |
| `ANDROID_HOME` | Replaces the untracked `local.properties`. |

Verified: with `local.properties` absent and only `ANDROID_HOME` set,
`./gradlew assembleDebug` succeeds.

### Debug keystore trap

Debug APKs are signed with a **per-user** keystore (`~/.android/debug.keystore`),
so a build from one machine will not install over a build from another —
Android rejects the signature change with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`
("App not installed"). Confirmed by comparing the committed APK against a
fresh local build:

| APK | Signer SHA-256 |
|---|---|
| Committed (built on `JUSTINELUISCALAGUAS`) | `3a540c8b0615248f...` |
| Built here (`ADMIN`) | `0e41d8c7466c2aad...` |

**Uninstall the old app before sideloading a new APK.** This clears its data.

## 5. Build outputs were tracked in git — `64ded46`

A single `assembleDebug` churned **450 tracked files** under `app/build/` and
`.gradle/` — 310 modified, 72 deleted, 68 new — burying the one real source
change. 574 paths were removed from tracking; the files stay on disk.

`__pycache__/` was already listed in `.gitignore` but stayed tracked, because
the rule never applies to files git already knows about. It is untracked now.

`local.properties` was tracked and pointed at
`C:\Users\JUSTINELUISCALAGUAS\AppData\Local\Android\Sdk`, a profile that does
not exist on this machine, so every build failed until it was corrected. Its
own header says it must not be committed.

## 6. What you need to do

**On pull**, git deletes `local.properties` from your working tree. Set
`ANDROID_HOME` to your SDK path before your next build:

```powershell
[Environment]::SetEnvironmentVariable('ANDROID_HOME', "$env:LOCALAPPDATA\Android\Sdk", 'User')
```

Then build with JDK 17:

```powershell
cd drowsiness_detector\android\DrowsinessAlertApp
$env:JAVA_HOME = "C:\Program Files\Microsoft\jdk-17.0.20.8-hotspot"
.\gradlew assembleDebug
```

**Uninstall the existing alert app on your phone** before installing the new
APK — see the keystore note in section 4.
